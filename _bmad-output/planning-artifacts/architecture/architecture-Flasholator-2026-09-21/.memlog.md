- (constraint) La SPEC existante impose l ordre : tests de caractérisation ; conventions MVVM/Riverpod ; flashcards/review ; traduction/tables ; auth/profil ; statistiques/monétisation ; retrait progressif du legacy.
- (constraint) Firebase, Drift, RevenueCat et la localisation générée sont préservés ; les fichiers l10n générés et db_wrapper.g.dart ne sont jamais modifiés directement.
- (direction) Parcours rapide demandé ; le spine build-substrate est le seul livrable.
- (decision) AD-1 [ADOPTED]: le paradigme cible est MVVM par fonctionnalité avec couche data et domaine optionnel. Les vues dépendent seulement de leurs ViewModels et composants de présentation ; les ViewModels dépendent des ports de cas d usage ou repositories ; les repositories dépendent des services/adaptateurs d infrastructure ; aucune dépendance ne remonte. Cela empêche les widgets d appeler Drift, Firebase, DeepL, RevenueCat, AdMob ou les préférences.
- (decision) AD-2 [ADOPTED]: Riverpod est l unique mécanisme d injection et d état applicatif. Les providers d infrastructure, repositories, cas d usage et ViewModels sont définis près de leur propriétaire et publics seulement au point de consommation requis ; ils sont surchargeables avec ProviderScope en test. Cela empêche les constructeurs concrets, singletons et Map globaux de devenir des voies parallèles de mutation.
- (decision) AD-3: chaque ViewModel expose un état UI immuable, typé et exhaustif (données, chargement, erreur, actions possibles). Les vues rendent cet état et délèguent les intentions ; aucun calcul métier, I/O, orchestration ou état durable ne vit dans une vue ou un StatefulWidget. Les libellés et comportements d erreur existants sont préservés pendant migration.
- (decision) AD-4: les modèles de domaine et contrats de repository ne dépendent ni de Flutter ni des DTO Drift/Firebase/RevenueCat. Les services encapsulent une source externe unique ; les repositories possèdent le mapping, le cache, les stratégies de lecture/écriture et les erreurs. Cela empêche les types générés ou SDK externes de traverser les features.
- (decision) AD-5: FlashcardRepository est l unique propriétaire de la collection locale et des opérations de paire réversible. Ajout, édition et suppression d une paire sont transactionnels ; lecture et révision restent compatibles avec les enregistrements existants et les règles SM-2 observées. Toute évolution de schéma Drift suit une migration explicite et régénère db_wrapper.g.dart.
- (decision) AD-6: UserSessionRepository est l unique propriétaire de l état de session partagé (authentification, profil cache, droits de traduction, abonnement et paire de langues). Les flux Firebase/Auth, Firestore, SharedPreferences et RevenueCat restent des adaptateurs ; les ViewModels ne lisent ou n écrivent pas de Map de données utilisateur.
- (decision) AD-7: la composition et l initialisation des SDK restent au bootstrap ; les clés et options sont injectées par configuration de plateforme. Les ViewModels et vues n initialisent pas Firebase, RevenueCat, AdMob, UMP/ATT ni ne portent de secrets. Cela préserve le bootstrap Firebase actuel et empêche des cycles de vie concurrents.
- (decision) AD-8: chaque tranche commence par des tests de caractérisation des comportements touchés puis migre une feature complète vers son remplaçant. Un élément legacy ne peut être supprimé qu après bascule de tous ses appelants, tests verts et aucune référence exécutable restante.
- (decision) AD-9 [ADOPTED]: les ARB sont la source de vérité de localisation ; app_localizations*.dart et db_wrapper.g.dart sont générés, jamais édités. L affichage de texte localisé reste dans les vues ou un adaptateur de présentation, jamais dans le domaine.
- (decision) AD-10: le contrat d exploitation reste iOS et Android, avec CI GitHub Actions exécutant flutter analyze et flutter test sur Flutter 3.32.5. Les opérations réseau restent dégradables hors-ligne selon leur comportement existant ; aucune synchronisation cloud des cartes n est introduite par cette migration.
- (version) Reality-check 2026-09-21: le projet verrouille Flutter 3.32.5 dans CI, flutter_riverpod 2.6.1, drift 2.28.1, firebase_core 3.15.2, firebase_auth 5.7.0, cloud_firestore 5.6.12, purchases_flutter/ui 9.2.0 et google_mobile_ads 6.0.0 dans pubspec.lock. Documentation officielle consultée : Flutter MVVM, Riverpod tests/overrides, Drift, Firebase Flutter, RevenueCat Flutter.
- (assumption) La migration n introduit ni synchronisation cloud des flashcards ni changement du contrat de stockage. Un futur identifiant de paire n est pas requis pour la migration comportementale actuelle.
- (question) L inventaire détaillé des composants legacy à supprimer reste piloté par la SPEC ; il sera actualisé tranche par tranche par la recherche de références exécutables.
- (direction) Le code cible migre les écrans actuels translation, review, data, authentication, profile et stats sans déplacer les intégrations préservées hors de leur adaptateur.
- (direction) Altitude corrigée à initiative : ce spine garde cohérentes les six features/tranches de migration, non un seul écran.
- (decision) AD-3 amended: les états UI ont phases communes initial/loading/data/error et erreur applicative typée ; les commandes mutantes sont sérialisées/idempotentes, requêtes remplaçables protégées par requestId/contexte, effets uniques non rejoués.
- (decision) AD-5 amended: le port expose opérations de paire et snapshots versionnés/flux invalidés après commit ; adaptateur Drift utilise AppDatabase.transaction. Tant que pairId est absent, clé canonique, recherche, précondition et mutation sont dans une transaction et mutations ciblent une paire exacte ; résultat typed applied/notFound/conflict.
- (decision) AD-6 amended: session machine à états anonymous/hydrating/authenticated/signingOut. Firebase auth est flux maître ; Firestore prime profil/droits, cache seulement accélérateur, RevenueCat prime entitlement. uid+generation invalident résultats tardifs ; logout purge cache, réconcilie RevenueCat et expose anonymous dernier.
- (decision) AD-7 amended: Firebase et Ads bootstrap avant ProviderScope ; RevenueCat est configuré une fois par adaptateur de session à partir de la session Firebase et identifié/déconnecté aux transitions. Les secrets d API ne sont jamais distribués dans le binaire ; TranslationRepository cible un relais authentifié. Rotation de la clé DeepL existante est une remédiation sécurité hors migration.
- (decision) AD-8 amended: la matrice de retrait legacy consigne composant, remplaçant, consommateurs migrés, tests et recherche de références ; suppression dans un changement Git dédié et réversible.
- (decision) AD-10 amended: CI qualité obligatoire sur push et pull_request ; versions Stack sont celles résolues par lockfile au 2026-09-21 et toute mise à jour est un changement de compatibilité testé.
- (decision) AD-11: StatisticsUseCase possède les projections statistiques partagées : dédoublonnage des paires, couples non orientés, séries/moyennes par paire et classements décroissants limités à cinq.
- (decision) AD-7 narrowed after review: le relais DeepL n est pas imposé dans la migration brownfield car aucun backend, ownership ni déploiement ne sont dans le périmètre. Le secret embarqué est une dette sécurité critique explicitement différée vers une architecture séparée ; la migration ne doit ni le déplacer ni en créer un autre.
